#92: Writing concurrent code that leads to false sharing
go func() {
for i := 0; i < len(inputs); i++ {
result.sumA += inputs[i].a
}
wg.Done()
}()
go func() {
for i := 0; i < len(inputs); i++ {
result.sumB += inputs[i].b
}
wg.Done()
}()
wg.Wait()
return result
}
We spin up two goroutines: one that iterates over each a field and another that iter-
ates over each b field. This example is fine from a concurrency perspective. For
instance, it doesn’t lead to a data race, because each goroutine increments its own
variable. But this example illustrates
the 
false 
sharing 
concept 
that
degrades expected performance.
 Let’s look at the main memory
(see figure 12.11). Because sumA and
sumB are allocated contiguously, in
most cases (seven out of eight), both
variables are allocated to the same
memory block.
 Now, let’s assume that the machine contains two cores. In most cases, we should
eventually have two threads scheduled on different cores. So if the CPU decides to
copy this memory block to a cache line, it is copied twice (figure 12.12).
