## What I Learned

### Database Normal Forms (Continuing from Chapter 1)

#### Boyce-Codd Normal Form (НФБК)
- **3NF (ЗНФ)** is insufficient when:
  - A table has **2+ candidate keys** (potential primary keys)
  - 2+ candidate keys are **composite** and share at least one common attribute
- A table is in **НФБК** if every non-trivial, irreducible functional dependency has a **candidate key** as its determinant (left side).
- **Example**: Parking reservation table with composite keys — `{lot_number, start_time}`, `{tariff, start_time}`. The functional dependency `tariff → lot_number` violates 3NF because `tariff` is not a candidate key → decompose into Tariffs table and Bookings table.

#### Fourth Normal Form (4НФ)
- Achieved when a table is in **НФБК** and all **multivalued dependencies** are actually **functional dependencies** on candidate keys.
- **Multivalued dependency**: `R.A ↠ R.B` means values of B depend only on A (not on C).
- **Example**: Restaurant menu — `{restaurant, pizza_type, delivery_area}`. Dependencies: `restaurant ↠ pizza_type` and `restaurant ↠ delivery_area`. Adding a new pizza type requires adding rows for every delivery area → decomposition into `restaurant-pizza` and `restaurant-delivery_area` tables.
- **Adding a function-dependent attribute** (e.g., price per `{restaurant, pizza, area}`) preserves 4NF.

#### Fifth Normal Form (5НФ)
- Achieved when a table is in 4NF and has no **join dependencies** (complex interdependencies where removing a row creates logical anomalies).
- **Example**: Suppliers/Products/Buyers — if Supplier A supplies Product X and Buyer B buys from Seller A, Seller A must also supply all products that Buyer B buys from others. This creates complex constraints requiring decomposition into separate Supplier, Product, and Buyer tables. In practice, 5NF is rarely achieved in pure form.

#### Domain-Key Normal Form (ДКНФ)
- Every constraint on the relation is a logical consequence of domain constraints and key constraints.
- Any table in ДКНФ is automatically in 5NF.
- **Not always achievable** — may require tradeoffs.

#### Sixth Normal Form (6НФ)
- Satisfies all **join dependencies** — cannot be decomposed without loss.
- **Not practically used** due to extreme normalization complexity.

### ACID Properties

| Property | Meaning |
|----------|---------|
| **Atomicity** | Transaction is all-or-nothing. Rollback on partial failure. |
| **Consistency** | Database moves from one consistent state to another. |
| **Isolation** | Concurrent transactions don't affect each other's results. |
| **Durability** | Once committed, the transaction persists permanently. |

### Transaction Isolation Levels

| Level | Solves | Description |
|-------|--------|-------------|
| **Read Uncommitted** | (None) | May read uncommitted (dirty) data |
| **Read Committed** | Dirty reads | Reads only committed data |
| **Repeatable Read** | Lost updates | Data read by a transaction cannot be modified by others |
| **Serializable** | Phantom reads | Transactions execute strictly sequentially |

**PostgreSQL behavior**: `Read Uncommitted` still doesn't allow dirty reads; `Repeatable Read` also prevents phantom reads.

### Concurrency Anomalies

| Anomaly | Description |
|---------|-------------|
| **Lost update** | Two transactions update the same data; one overwrites the other's changes. |
| **Dirty read** | Reading uncommitted data that gets rolled back by another transaction. |
| **Non-repeatable read** | A re-read of the same data returns different results within one transaction. |
| **Phantom read** | New rows added/removed by another transaction appear in re-queried result sets. |
| **Serialization anomaly** | Concurrent transactions produce inconsistent results vs any serial order. |

### Transaction Service Design

The Transaction service uses **double-entry bookkeeping** (borrowing/lending) where every operation is recorded as a **Transaction** with one or more **TransactionEntry** (debit/credit) records:

- **Transaction**: Header record (id, user_id, amount, type, status, timestamps)
- **TransactionEntry**: Line items (id, transaction_id, account_id, direction, amount)
- **Types**: Deposit, Withdraw, Transfer
- **Directions**: DEBIT (increase balance), CREDIT (decrease balance)
- **Statuses**: pending → completed / failed / cancelled

### Transaction Service Architecture

The `Transaction` proto contract defines:
- **Deposit**: Add funds to user's account
- **Withdraw**: Remove funds from user's account
- **Transfer**: Move funds from one user to another (credit sender, debit recipient)
- **GetTransactions**: List with filtering (by user_id, type, status, date range) and pagination

## Important Concepts

- **Double-entry bookkeeping**: Every transaction records both debit and credit entries — for transfers, the sender gets a credit entry and the recipient gets a debit entry.
- **Amount in копейках**: Stored as `int64` (cents) to avoid floating-point precision issues with financial calculations.
- **Atomicity**: All operations within a transaction succeed or fail together (using GORM's `Transaction()` wrapper or `db.Begin()`/`tx.Commit()`).
- **Soft delete**: `is_deleted` flag instead of hard delete — preserves transaction history integrity.
- **YAGNI principle**: Don't implement methods until needed ("You ain't gonna need it").

## Remember This

> Transaction isolation levels: Read Uncommitted → Read Committed → Repeatable Read → Serializable. PostgreSQL's Read Committed prevents dirty reads; Repeatable Read also prevents phantom reads.

> Database design normal forms: 3NF → НФБК (for composite/multiple keys) → 4NF (for multivalued dependencies) → 5NF (for join dependencies) → ДКНФ → 6НФ (rarely used in practice).

## Terms

- **Normal forms**: Database normalization rules (1NF through 6NF, Domain-Key NF)
- **Boyce-Codd NF (НФБК)**: Extension of 3NF where every determinant is a candidate key
- **Fourth Normal Form (4НФ)**: No multivalued dependencies
- **Fifth Normal Form (5НF)**: No join dependencies
- **Domain-Key NF (ДКНФ)**: All constraints are logical consequences of domain and key constraints
- **Sixth Normal Form (6НNF)**: Satisfies all join dependencies
- **Multivalued dependency**: Non-key attribute determines another (not functionally dependent)
- **Join dependency**: Decomposition/join constraint
- **Functional dependency**: When one attribute determines another
- **Candidate key**: Minimal set of attributes uniquely identifying a row
- **Determinant**: Attribute(s) on the left side of functional dependency
- **ACID**: Atomicity, Consistency, Isolation, Durability
- **Atomicity**: All-or-nothing transaction execution
- **Consistency**: Valid state before and after transaction
- **Isolation**: Transaction isolation from concurrent operations
- **Durability**: Committed changes persist permanently
- **Lost update**: Two concurrent updates; one overwrites the other
- **Dirty read**: Reading uncommitted data
- **Non-repeatable read**: Same query returns different data within a transaction
- **Phantom read**: New/deleted rows appear in re-queried result sets
- **Serialization anomaly**: Concurrent transactions produce an inconsistent result
- **Double-entry bookkeeping**: Every debit has a matching credit
- **Debit/Кредит**: Debit increases balance; Credit decreases balance
- **Transaction status**: pending, completed, failed, cancelled
- **Transaction type**: deposit, withdraw, transfer
- **YAGNI**: "You ain't gonna need it" — implement only what's needed now
- **Soft delete**: Mark as deleted via flag instead of removing
- **копейка (kopeyka)**: Minor currency unit; amounts stored as integers to avoid float issues

## Notes

- Transaction service starts at page 167/168 — the proto contract defines Deposit, Withdraw, Transfer, GetTransactions, plus filtering and pagination.
- Amounts stored as int64 (cents/kopeyki) to avoid floating-point precision issues — critical for financial operations.
- The Transaction service doesn't have its own users table — it references `user_id` from the Account service. Account service gets a `balance` field and `is_deleted` flag.
- `is_deleted` (soft delete) prevents foreign key violations — financial transactions must outlive user accounts.
- Docker Compose uses ports 5432/5433/5434 for the three PostgreSQL databases.
- Migration order for rollback: drop indexes → drop primary keys → drop tables (reverse order to maintain FK integrity).
