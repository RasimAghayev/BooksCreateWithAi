### Transaction Service Layer (listing 4.10)

The TransactionService is a thin business logic layer that wraps the Repository:

```go
type TransactionService struct {
    repo   Repository
    logger *zerolog.Logger
}

type Repository interface {
    // Read operations
    GetTransactions(context.Context, model.GetTransactionsParams) ([]model.Transaction, error)
    GetTransactionDetails(context.Context, uint64) (model.TransactionDetails, error)
    // Financial operations
    Deposit(context.Context, model.DepositParams) (model.TransactionDetails, error)
    Withdraw(context.Context, model.WithdrawParams) (model.TransactionDetails, error)
    Transfer(context.Context, model.TransferParams) (model.TransactionDetails, error)
}

func New(repo Repository, logger *zerolog.Logger) *TransactionService {
    return &TransactionService{repo: repo, logger: logger}
}
```

#### GetTransactionsWithDetails
```go
func (s *TransactionService) GetTransactionsWithDetails(ctx context.Context, params model.GetTransactionsParams) ([]model.TransactionDetails, error) {
    transactions, err := s.repo.GetTransactions(ctx, params)
    if err != nil {
        s.logger.Error().Err(err).Msg("failed to get transactions")
        return nil, err
    }
    var transactionDetails []model.TransactionDetails
    for _, transaction := range transactions {
        details, err := s.repo.GetTransactionDetails(ctx, transaction.ID)
        if err != nil {
            s.logger.Error().Err(err).Uint64("transaction_id", transaction.ID).Msg("failed to get transaction details")
            continue  // Skip failed transactions
        }
        transactionDetails = append(transactionDetails, details)
    }
    return transactionDetails, nil
}
```

#### Business Operation Methods (thin wrappers)
```go
func (s *TransactionService) Deposit(ctx context.Context, userID uint64, amount float64) (model.TransactionDetails, error) {
    params := model.DepositParams{UserID: userID, Amount: amount}
    return s.repo.Deposit(ctx, params)
}

func (s *TransactionService) Withdraw(ctx context.Context, accountID uint64, amount float64) (model.TransactionDetails, error) {
    params := model.WithdrawParams{AccountID: accountID, Amount: amount}
    return s.repo.Withdraw(ctx, params)
}

func (s *TransactionService) Transfer(ctx context.Context, userID, recipient uint64, amount float64) (model.TransactionDetails, error) {
    params := model.TransferParams{UserID: userID, Recipient: recipient, Amount: amount}
    return s.repo.Transfer(ctx, params)
}
```

> "Помимо баланса, мы добавили сюда также поле isDeleted, по которому будем отличать активных пользователей от удаленных."

Soft delete preserves transaction reference integrity.

## Important Concepts

- **Service layer thinness**: TransactionService is a thin wrapper around Repository — most logic lives in the repository's DB transactions.
- **Soft delete pattern**: `is_deleted` flag instead of hard DELETE — preserves referential integrity for financial records.
- **GetTransactionsWithDetails**: Fetches transaction list, then N+1 queries for details — the author skips failed ones with `continue`.
- **Proto versioning**: After every contract change, regenerate proto code and pull into services.
- **Balance as float in proto**: Stored as `float` in proto but converted to `int64` (cents) in repository for storage — tradeoff between API simplicity and financial precision.
- **Balance operations have operation_id**: Allows idempotency for external callers (duplicate detection).

## Remember This

> Soft delete is mandatory for financial systems — transactions reference users; hard-deleting users would break referential integrity.

> Account service now exposes Deposit, Withdraw, Transfer, GetBalance methods — the Transaction service will call these for balance updates.

## Terms

- **TransactionService**: Business logic layer for Transaction service
- **Service layer**: Thin wrapper over Repository with minimal logic
- **is_deleted flag**: Soft delete marker in user records
- **is_deleted (proto)**: Boolean field for identifying deleted accounts
- **operation_id**: Unique identifier for idempotency on financial operations
- **GetTransactionsWithDetails**: Aggregates transaction + entries for each record
- **N+1 query problem**: Fetching details in a loop after initial list query
- **Proto regeneration**: Required after every contract update

## Notes

- The Account service gets new RPC methods (Deposit, Withdraw, Transfer, GetBalance) — these will be called by the Transaction service to update balances.
- The Transaction service and Account service both have Deposit/Withdraw/Transfer methods — Transaction manages the transaction records, Account manages the actual balance changes.
- The `operation_id` field in proto requests enables idempotency — critical for financial systems where retries might occur.
- The soft delete pattern (is_deleted) is applied across the Account service — all queries must filter `is_deleted = false`.
