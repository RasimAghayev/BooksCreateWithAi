## Main Idea

This section covers the **Saga pattern implementation** using Kafka as the message broker. The Transaction service publishes balance operation requests to Kafka, and the Account service consumes them, performs the operations, and publishes responses. The Transaction service then listens for responses and updates transaction status accordingly. This avoids distributed transactions (which violate ACID) by using asynchronous event-driven communication.

## What I Learned

### Saga Pattern with Kafka

#### Problem Statement
The Transaction service operates across its own database (for transaction records) and the Account service's database (for balance updates). Using two separate databases breaks ACID — if one database commits and the other fails, data becomes inconsistent.

#### Solution: Saga Pattern
```
Transaction Service            Kafka             Account Service
     │                         │                        │
     │ 1. Create transaction  │                        │
     |    (status=pending)     │                        │
     │                         │                        │
     │ 2. Publish request      │                        │
     │    → "transaction_data" │                        │
     │                         │                        │
     │                         │ 3. Consume request     │
     │                         │                        │
     │                         │ 4. Update balance      │
     │                         │    (deposit/withdraw/  │
     │                         │     transfer)          │
     │                         │                        │
     │                         │ 5. Publish response    │
     │                         │    ← "transaction_     │
     │                         │      response"         │
     │                         │                        │
     │ 6. Consume response     │                        │
     │    (update status)      │                        │
     │    completed/f failed   │                        │
```

#### Deposit Implementation (via Kafka)
```go
func (s *TransactionService) Deposit(ctx context.Context, userID uint64, amount float64) (model.TransactionDetails, error) {
    params := model.DepositParams{UserID: userID, Amount: amount}
    
    // 1. Create transaction in pending status
    res, err := s.repo.Deposit(ctx, params)
    if err != nil {
        return model.TransactionDetails{}, err
    }
    
    // 2. Send deposit request via Kafka (async)
    request := map[string]interface{}{
        "request_type": "deposit",
        "user_id": userID,
        "amount": int64(amount * 100),  // convert to kopeyki
        "operation_id": res.Transaction.ID,
        "timestamp": time.Now().UTC(),
    }
    err = s.kafkaPublisher.Publish(ctx, "transaction_data", fmt.Sprintf("%d", userID), request)
    if err != nil {
        // Kafka send failed → mark as failed, rollback is impossible
        updateErr := s.repo.UpdateTransactionStatus(ctx, res.Transaction.ID, model.TransactionStatusFailed)
        return model.TransactionDetails{}, err
    }
    
    // Transaction stays in pending until Account service responds
    return res, nil
}
```

#### HandleAccountResponse (listing 4.34)
Processes Kafka responses from Account service:

```go
type AccountResponse struct {
    RequestType string `json:"request_type"`
    UserID      uint64 `json:"user_id"`
    OperationID uint64 `json:"operation_id"`
    Result      bool   `json:"result"`
}

func (s *TransactionService) HandleAccountResponse(ctx context.Context, topic string, key string, data []byte) error {
    var response AccountResponse
    if err := json.Unmarshal(data, &response); err != nil {
        return fmt.Errorf("failed to unmarshal account response: %w", err)
    }
    if response.RequestType == "" || response.UserID == 0 || response.OperationID == 0 {
        return fmt.Errorf("missing or invalid")
    }
    
    // Update transaction status based on result
    var status model.TransactionStatus
    var logMsg string
    if response.Result {
        status = model.TransactionStatusCompleted
        logMsg = "transaction completed successfully"
    } else {
        status = model.TransactionStatusFailed
        logMsg = "transaction failed"
    }
    
    err := s.repo.UpdateTransactionStatus(ctx, response.OperationID, status)
    if err != nil {
        return fmt.Errorf("failed to update transaction status to %s: %w", status, err)
    }
    s.logger.Info().Uint64("operation_id", response.OperationID).Msg(logMsg)
    return nil
}
```

```go
    OperationID uint64      `json:"operation_id"`
    Result      interface{} `json:"result"`
}
```

#### HandleTransaction (Account side)
Consumes messages from Kafka and processes them:

```go
func (s *AccountService) HandleTransaction(ctx context.Context, topic string, key string, data []byte) error {
    s.logger.Info().Msg("handling transaction request")
    
    var res TransactionRequest
    if err := json.Unmarshal(data, &res); err != nil {
        return fmt.Errorf("failed to unmarshal: %w", err)
    }
    
    result := map[string]interface{}{
        "request_type":  res.RequestType,
        "user_id":       res.UserID,
        "operation_id":  res.OperationID,
        "result":        false,
    }
    
    var err error
    switch res.RequestType {
    case "withdraw":
        _, err = s.Withdraw(ctx, res.UserID, res.Amount)
    case "deposit":
        _, err = s.Deposit(ctx, res.UserID, res.Amount)
    case "transfer":
        _, _, err = s.Transfer(ctx, res.UserID, res.RecipientID, res.Amount)
    default:
        err = fmt.Errorf("unknown request type: %s", res.RequestType)
    }
    
    if err != nil {
        // Publish failure response
        s.kafkaPublisher.Publish(ctx, "transaction_response", "key", result)
        return fmt.Errorf("failed to handle: %w", err)
    }
    
    // Publish success response
    result["result"] = true
    s.kafkaPublisher.Publish(ctx, "transaction_response", strconv.FormatUint(res.UserID, 10), result)
    return nil
}
```

#### Account Service App Wiring (listing 4.37)
The Account service wires up Kafka similarly to Transaction service:

```go
type App struct {
    cfg                *config.Config
    logger             *zerolog.Logger
    accountRepository  *repository.Repository
    accountService     *service.AccountService
    accountServer      *server.Server
    grpcServer         *grpc.Server
    kafkaClient        *kafka.Kafka
}

func (a *App) getAccountService(ctx context.Context) (*service.AccountService, error) {
    repo, err := a.getRepository(ctx)
    kafkaClient, err := a.getKafkaClient(ctx)
    a.accountService = service.New(repo, kafkaClient, a.logger)
    
    // Subscribe to transaction requests
    a.kafkaClient.Subscribe(ctx, a.cfg.KafkaTransactionTopic, a.accountService.HandleTransaction)
    a.logger.Info().Msg("kafka client attached to transaction service")
    return a.accountService, nil
}
```

The Saga pattern with Kafka provides eventual consistency — transactions are eventually completed/failed, not immediately consistent.

> "Это позволяет использовать его как центральный компонент системы авторизации, изолированный от деталей базы данных и инфраструктуры."

Services are loosely coupled via events — Account and Transaction don't know about each other directly.

## Important Concepts

- **Saga pattern**: Manages data consistency across distributed services using local transactions + compensating actions.
- **Event-driven architecture**: Services communicate via events published/consumed through Kafka — loose coupling.
- **Eventual consistency**: Transactions start in `pending` state and are updated to `completed`/`failed` when the Account service responds — there's a window where state is inconsistent.
- **Compensating transactions**: When a balance operation fails, the transaction status is updated to `failed` — the failure is "compensated" by status update (not by reversing any balance changes).
- **Idempotency key**: `operation_id` (transaction ID) prevents duplicate processing.
- **Kafka configuration**: Producer (publishes messages) + Consumer (subscribes to topics). Each topic can have its own consumer group.
- **Topics**: `transaction_data` (requests), `transaction_response` (responses), `transaction_request` (alternative topic name in Account config).

## Remember This

> Saga pattern: Create transaction (pending) → Publish request to Kafka → Account processes + publishes response → Transaction service updates status (completed/failed). No distributed transactions — eventual consistency.

> The `operation_id` field (mapped to transaction ID) enables idempotent processing — the Account service can detect duplicate requests.

## Terms

- **Saga pattern**: Distributed transaction pattern with local transactions + compensating actions
- **Eventual consistency**: Data converges over time, not immediately
- **Compensating transaction**: Action to undo a completed operation
- **Kafka Publisher**: Component that sends messages to Kafka topics
- **Kafka Consumer**: Component that reads messages from Kafka topics
- **Topic**: Kafka message category (e.g., transaction_data, transaction_response)
- **Consumer group**: Set of consumers sharing partition consumption
- **Producer**: Kafka client that writes messages
- **Reader/Writer**: segmentio/kafka-go's Kafka client primitives
- **Message handler**: Function invoked for each consumed message
- **operation_id**: Unique identifier mapping response to transaction (idempotency)
- **pending/completed/failed**: Transaction lifecycle states
- **event-driven**: Architecture where services react to published events
- **loose coupling**: Services don't directly depend on each other

- The Saga pattern implements **eventual consistency**: Transaction service publishes to `transaction_data` topic, Account service consumes, processes, and publishes response to `transaction_response` topic.
