## Main Idea

This section covers Redis (in-memory key-value store used as cache/store complement), the API Gateway pattern as a facade service, and the JWT interceptor for centralized authentication. It details the Gateway proto contract, the interceptor implementation for validating JWT tokens, and the app lifecycle setup.

## What I Learned

### Redis

- **Redis**: In-memory key-value store organized in RAM. Used as a complement to disk-based databases (PostgreSQL, MySQL, MongoDB).
- **Why Redis**: Disk-based DBs are updated infrequently but queried often; Redis stores frequently accessed/changing data in fast memory.
- **Tradeoff**: Memory is expensive; Redis can't fully replace disk-based DBs.
- **Use cases**:
  - Rarely changing data accessed frequently (headers, API keys needing validation)
  - Frequently changing non-critical data (generated reports that change often)
- **Supported data structures**: strings, hash tables, bitmaps, lists, sets, bit fields, sorted sets, geospatial data, HyperLogLog, streams.
- **Beyond caching**: Used for queues, stream processing, and as a message broker.

### API Gateway Pattern

The **API Gateway** is a facade (tamozhnya / diriger) service that:
- Acts as the single entry point for all external clients
- Validates authentication/authorization on every request
- Routes/dispatches requests to the correct internal service
- Transforms request format (e.g., HTTP → gRPC)
- Aggregates data from multiple services into a single response
- Handles cross-cutting concerns: token validation, rate limiting, caching, API versioning, data aggregation

#### Benefits:
- Clients only need to know one address (the Gateway)
- Each request requires only one authentication check
- Changes in internal topology don't require client-side code changes
- Centralized infrastructure logic (reduces duplication)
- Better security and monitoring

#### Gateway Proto Contract (listing 3.1):
- Combines auth + account endpoints into a unified `Gateway` service
- Uses `google.api.http` annotations for REST mapping
- Public methods: Register, Login, Refresh, Logout, ValidateToken
- Protected methods (require auth): CreateUser, GetUser, GetCurrentUser, GetUsers, UpdateUser, UpdateCurrentUser, DeleteUser, DeleteCurrentUser
- `GetCurrentUser`, `UpdateCurrentUser`, `DeleteCurrentUser` get `user_id` from the JWT token (not from request body)
- Imports: `account/account_model.proto`, `auth/auth_model.proto`, `pagination/pagination.proto`, `google/api/annotations.proto`, `google/protobuf/empty.proto`

### JWT Interceptor

The **JWT Interceptor** centralizes authentication in the Gateway:
- **Unary Interceptor**: Intercepts normal RPC calls (one request → one response)
- **Stream Interceptor**: Intercepts streaming RPC calls
- **Public methods**: Register, Login, Refresh — skip auth check (no token yet)
- **Private methods**: Require valid JWT in `Authorization: Bearer <token>` header
- **Process**:
  1. Check if method is public → skip auth
  2. Extract Bearer token from metadata
  3. Remove "Bearer " prefix
  4. Parse and validate JWT using secret key (HMAC algorithm check)
  5. Extract `user_id` from JWT claims
  6. Add `user_id` to request context
  7. Forward to business logic handler

#### JWT Claims Struct:
```go
type JWTClaims struct {
    UserID uint64 `json:"user_id"`
    jwt.RegisteredClaims
}
```

#### Interceptor Config:
- `JWT_SECRET=secret` — secret key for signing/validating tokens
- `AuthGrpcHost=localhost:50052` — Auth service address (Gateway forwards auth calls)
- `AccountGrpcHost=localhost:50051` — Account service address
- `GRPC_PORT=50053` — Gateway's own gRPC port

### Gateway App Lifecycle

The `App` struct coordinates:
- **gRPC server setup**: Creates gRPC server with JWT interceptor
- **Service clients**: Lazy-creates gRPC clients for Auth and Account services
- **Gateway service**: Orchestrates calls between Auth and Account services
- **Graceful shutdown**: `GracefulStop()` on context cancellation

#### Gateway Service Interface (listing 3.7):
```go
type GatewayService struct {
    accountService AccountService  // interface
    authService    AuthService     // interface
}

type AccountService interface {
    CreateUser(ctx, model.User) (model.User, error)
    GetUser(ctx, uint64) (model.User, error)
    GetUsers(ctx, uint32, uint32) ([]model.User, error)
    DeleteUser(ctx, uint64) error
    UpdateUser(ctx, uint64, model.UpdateUser) error
}

type AuthService interface {
    Login(ctx, string, string) (model.TokenPair, error)
    Logout(ctx, string) error
    Register(ctx, uint64, string, string, string) error
    Verify(ctx, string) (uint64, error)
    Refresh(ctx, string) (model.TokenPair, error)
    DeleteUser(ctx, uint64) error
}
```

#### Registration flow:
1. Create user in Account service (password NOT sent to Account)
2. Register user in Auth service (password hashed with bcrypt)
3. Login immediately to return token pair

#### Server layer:
- Translates proto messages ↔ Go models (mapper layer)
- Calls GatewayService methods
- For `GetCurrentUser`/`UpdateCurrentUser`/`DeleteCurrentUser`: gets `user_id` from context (set by interceptor)

## What the Author Is Saying

> "Gateway работает как фасад. Он принимает запрос, проверяет авторизацию и аутентификацию. Может добавить или изменить заголовки, преобразовать входной формат в нужный внутренним сервисам вид, а затем пересылает вызов дальше."

The Gateway is more than a router — it's a transformation and orchestration layer.

> "Для того чтобы передавать дополнительную информацию в токене, принято использовать JWTClaims — структуру с пользовательскими «претензиями» (claims), которые включают в себя стандартные поля токена и дополнительное поле UserID."

Custom JWT claims allow embedding user identity directly in the token.

> "При следующих вызовах сервисов, которые будут происходить из Gateway, нет необходимости проверять JWT каждый раз"

The JWT interceptor runs once at the Gateway — internal services trust the Gateway's context.

## Important Concepts

- **Facade pattern**: Gateway hides internal service complexity behind a unified API.
- **Centralized auth**: JWT validation happens once at the Gateway; internal services receive authenticated user_id from context.
- **Public vs private methods**: The interceptor defines which gRPC methods skip auth (Register, Login, Refresh) and which require it.
- **Token propagation**: Gateway creates gRPC clients to call Auth/Account services; the authenticated user_id flows via context (not re-validated per call).
- **gRPC interceptors**: Middleware for RPC handlers — analogous to HTTP middleware in web frameworks.
- **Lazy initialization**: Service clients are created on first use (`if a.authService == nil`).
- **Separation of concerns**: mapper layer isolates proto-generated code from internal domain models.

## Remember This

> The Gateway pattern: single entry point → centralized auth → request routing → data aggregation. Internal services remain hidden and don't re-validate tokens.

> JWT Interceptor pipeline: 1) Check public method → 2) Extract Bearer token → 3) Validate JWT signature → 4) Extract user_id → 5) Add to context → 6) Forward to handler.

## Terms

- **Redis**: In-memory key-value store (RAM-based)
- **API Gateway**: Facade service for external client requests
- **Facade pattern**: Simplified interface hiding complex subsystem
- **JWT Interceptor**: gRPC middleware for JWT validation
- **Unary Interceptor**: Intercepts unary (single request-response) RPC calls
- **Stream Interceptor**: Intercepts streaming RPC calls
- **Public methods**: gRPC methods that skip authentication (Register, Login, Refresh)
- **Private methods**: gRPC methods requiring authentication
- **Bearer prefix**: `Bearer ` prefix for JWT tokens in Authorization header
- **Metadata**: gRPC request metadata (headers)
- **Context propagation**: Passing user_id via Go context.Context
- **Mapper layer**: Proto ↔ Go model conversion
- **Lazy initialization**: Creating resources on first use
- **Graceful shutdown**: `GracefulStop()` waits for active RPCs to complete
- **Cross-cutting concerns**: Auth, rate limiting, caching, logging, monitoring
