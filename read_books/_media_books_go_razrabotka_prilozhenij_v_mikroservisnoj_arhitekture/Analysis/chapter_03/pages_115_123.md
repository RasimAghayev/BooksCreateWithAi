### HTTP Protocol Structure (continued)

#### HTTP Request
1. **HTTP method** (GET, POST, PUT, PATCH, DELETE, CONNECT, OPTIONS, TRACE)
2. **Resource path** (URL string)
3. **HTTP protocol version**
4. **Headers** (optional) — contain metadata like authorization tokens
5. **Request body** — for POST/PUT methods

Example:
```
GET /api/v1/user
Host: localhost:9000
```

#### HTTP Response
1. **HTTP protocol version**
2. **HTTP status code** (1xx-5xx, five groups):
   - 1xx: Informational
   - 2xx: Successful
   - 3xx: Redirected
   - 4xx: Client errors (e.g., 404 Not Found)
   - 5xx: Server errors
3. **Status message** — brief description (e.g., "Record not found", "OK")
4. **Headers** — metadata
5. **Response body** — optional response data

### gRPC and Protocol Buffers

- **gRPC** uses HTTP/2 + Protobuf for inter-service communication. Supported by all major languages (Go, Java, Node.js, C++, Python, etc.).
- **Protobuf**: Binary protocol — more compact, simple, and fast than XML. Uses `.proto` files to define message format and services.
- **Message format example**:
```
message User {
  string user_id = 1;
  string login = 2;
  string phone = 4;
  string firstName = 5;
  string lastName = 6;
}
```
- **Field indexing**: Each field has an index number (`= 1`, `= 2`). Names can differ across services, but matching indices/types can cause confusion — consistency is critical.
- **Shared contracts repository**: Common `.proto` files in a separate repo ensure consistent message formats across all projects.
- **gRPC service definition** with annotations for REST gateway:
```
syntax = "proto3";
import "google/api/annotations.proto";
service UserService {
  rpc GetUsers(UsersRequest) returns (UsersResponse) {
    option (google.api.http) = { get: "/api/v1/users" };
  }
}
```

### RabbitMQ (AMQP Protocol)

- **RabbitMQ**: Message broker based on AMQP (Advanced Message Queuing Protocol) — open standard for exchanging messages with low latency and high speed.
- **AMQP Model**: Client-server architecture where:
  - **Message**: Unit of data with content + optional structured headers
  - **Exchange**: Message goes here; distributes to queues. Types:
    - **Fanout**: Sends to ALL bound queues (broadcast)
    - **Direct**: Routes to queue with matching routing key
    - **Topic**: Middle ground — routes to queues with matching routing key mask (e.g., `app.notification.sms.*`)
  - **Queue**: Stores messages until consumed
  - **Message broker**: Server that accepts, stores, and routes messages
  - **Producer/Publisher**: Service sending messages
  - **Consumer**: Service receiving messages
- **Delivery guarantees** (levels):
  - **At Most Once**: No retries; message may be lost. Fastest.
  - **At Least Once**: Retry until acknowledgment; message may be delivered multiple times.
  - **Exactly Once**: Delivered exactly once without loss or duplication (hardest to implement; usually handled at application level with idempotency).
- **Channels**: Multiple isolated communication channels per connection. Each channel has its own state. Opening new connections for each operation is wasteful; reuse channels.
- **Use cases**: Background processing (e.g., generating reports), event bus pattern.

### Kafka

- **Kafka**: Another message broker like RabbitMQ, but with different architecture.
- **Request model**: 
  - **Pull**: Consumer polls server for new messages periodically (can batch for higher throughput). May cause latency and load imbalance.
  - **Push**: Server pushes messages to clients. No backlog but requires flow control limits (QOS).
  - Kafka uses **pull**; RabbitMQ uses **push**.
- **Message retention**:
  - **Kafka**: Messages stay in storage even after consumption — can be re-consumed by different consumers in different contexts.
  - **RabbitMQ**: Messages are deleted after consumption.
- **Kafka architecture**:
  - **Producers**: Send messages to topics
  - **Topics**: Categories of messages, divided into **partitions**
  - **Partitions**: Ordered, indexed log of messages (by offset)
  - **Consumers**: Read from partitions
  - **Streams API**: Reads and writes data to Kafka
- **Topic types**:
  - **Regular topics**: Configurable retention time or size limit; oldest entries deleted when limit exceeded.
  - **Compact topics**: No retention/time limit; retains only the latest value for each key. Manual deletion via null values.
- **Kafka Connect**: Framework for importing/exporting data to/from external systems via connectors.
- **Kafka vs RabbitMQ**: Kafka excels at event streaming and re-processing; RabbitMQ at simple pub/sub with immediate consumption.

## Important Concepts

- **Fanout vs Direct vs Topic exchanges**: Different routing strategies for message distribution.
- **Delivery guarantees**: AtMostOnce (fastest, can lose), AtLeastOnce (reliable but may duplicate), ExactlyOnce (hardest, most robust).
- **Pull vs Push**: Kafka's pull model allows batching and backpressure control; RabbitMQ's push model reduces latency.
- **Message retention in Kafka vs RabbitMQ**: Kafka retains messages for replay; RabbitMQ deletes after consumption.
- **Channels vs Connections**: Multiple channels per connection reduce overhead; don't open a new connection per operation.
- **Kafka partitions**: Messages ordered within a partition but not across partitions — important for ordering guarantees.
- **Kafka compaction**: Compacts messages by key — only latest value per key is retained.

## Remember This

> RabbitMQ uses push model + deletes messages on consumption; Kafka uses pull model + retains messages for replay. Choose RabbitMQ for simple pub/sub, Kafka for event streaming and reprocessing.

> AMQP delivery levels: AtMostOnce (loss possible) → AtLeastOnce (duplicates possible) → ExactlyOnce (hardest, handle at app level).

## Terms

- **AMQP**: Advanced Message Queuing Protocol
- **Exchange**: AMQP message router (Fanout, Direct, Topic types)
- **Queue**: Message storage until consumption
- **Fanout exchange**: Broadcast to all queues
- **Direct exchange**: Route by exact routing key match
- **Topic exchange**: Route by routing key pattern match
- **Producer/Publisher**: Message sender service
- **Consumer**: Message receiving service
- **Channel**: Isolated communication path within a connection
- **At Most Once delivery**: No retry; may lose messages
- **At Least Once delivery**: Retry until ack; may duplicate messages
- **Exactly Once delivery**: No loss, no duplication (hard; app-level solution)
- **Pull model**: Consumer polls for messages
- **Push model**: Server pushes messages to consumer
- **Topic**: Kafka message category
- **Partition**: Ordered log of messages within a topic
- **Offset**: Position index within a partition
- **Retention**: How long Kafka stores messages
- **Compacted topic**: Keeps only latest value per key
- **Kafka Connect**: Data import/export framework
- **Streams API**: Kafka library for stream processing
- **QOS (Quality of Service)**: Flow control limit for Push model
