## Main Idea

Chapter 5 covers deployment strategies for microservices and introduces CI/CD automation using GitHub Actions. It covers five deployment approaches (single VM, multi-VM, containers, Kubernetes, serverless) and walks through setting up nginx as a reverse proxy/balancer, then creating GitHub Actions workflows for building, linting, and testing.

## What I Learned

### Deployment Strategies (5 approaches)

1. **One server, several processes**: Local development style — multiple processes on different ports on a single VM. Good for testing, bad for production (single point of failure).

2. **Several servers, several processes**: Scale horizontally by adding more VMs behind a load balancer (nginx/Apache). Better fault tolerance but requires more manual setup.

3. **Containers**: Package microservices in Docker containers for portability and consistent environments. This is the first step toward Kubernetes orchestration.

4. **Orchestrator (Kubernetes/Nomad)**: Full container orchestration platform for running many containers at scale. Handles scaling, networking, service discovery, rolling updates.

5. **Serverless**: Run code directly in the cloud without managing servers, processes, or containers. Pay-per-execution model.

### Nginx Reverse Proxy Configuration

For the "multiple servers" deployment approach, nginx acts as a load balancer/proxy:

```bash
# Install nginx on Ubuntu 24.04
sudo apt install nginx

# Check status
sudo systemctl status nginx
```

Configuration file: `/etc/nginx/sites-available/default`

```nginx
location / {
    proxy_pass http://localhost:50053;  # Proxy to Gateway service
}
```

**Limitations**: Manual setup (clone code, install Docker Compose, start services), services die when SSH disconnects, nginx config is tedious for multiple instances.

### CI/CD with GitHub Actions

GitHub Actions automates:
- Test execution
- Code linting
- Code formatting checks
- Build verification
- Deployment (staging)

#### Workflow Creation
1. Upload service code to GitHub (create repository)
2. Navigate to **Actions** tab
3. Click **set up a workflow yourself**
4. Create a YAML file in `.github/workflows/`

#### Basic Workflow (listing 5.1)
```yaml
name: Transaction
on: workflow_dispatch  # Manual trigger

jobs:
  stage_dev:
    runs-on: ubuntu-latest
    steps:
      - name: lint
        run: echo Hello
```

#### Workflow Parameters
- **name**: Arbitrary workflow name (service name or stage name)
- **on**: Trigger event — `workflow_dispatch` (manual), `push`, `pull_request`, branch-specific, etc.
- **jobs**: Work to be executed
- **stage_dev**: Arbitrary name for the first job
- **runs-on**: OS to run on (ubuntu-latest, macos-latest, windows-latest)
- **steps**: Ordered execution steps
- **uses**: Use a pre-built action (e.g., `actions/checkout@v4.5.3`)
- **run**: Execute shell command(s)

#### Complete Workflow with Checkout + Testing (listing 5.2)
```yaml
name: Transaction
on: workflow_dispatch

jobs:
  stage_dev:
    runs-on: ubuntu-latest
    steps:
      - name: get code
        uses: actions/checkout@v4.5.3
      - name: install deps
        run: go mod download
```

#### Makefile (listing 5.3)
Comprehensive Makefile for Go microservices:
```makefile
APP_NAME ?= transaction
BINARY_NAME ?= bin/$(APP_NAME)
MAIN_PATH ?= ./cmd
VERSION ?= $(shell git describe --tags --always --dirty 2>/dev/null || echo "dev")
BUILD_TIME ?=$(shell date -u '+%Y-%m-%d_%H:%M:%S')
LDFLAGS ?=-ldflags "-X main.Version=$(VERSION) -X main.BuildTime=$(BUILD_TIME)"

GOFILES ?=$(shell find . -name "*.go" -type f -not -path "./vendor/*" -not -path "./.git/*")

.DEFAULT GOAL := build

build:
	@echo "Building $(APP_NAME) ..."
	@mkdir -p bin
	go build $(LDFLAGS) -o $(BINARY_NAME) $(MAIN_PATH)

run: clean build
	@echo "Running $(APP_NAME) ..."
	./$(BINARY_NAME)

deps:
	@echo "Installing dependencies ..."
	go mod download
	go mod tidy

deps-update:
	@echo "Updating dependencies ..."
	go get -u ./...
	go mod tidy

fmt:
	@echo "Formatting code ..."
	gofmt -s -w $(GOFILES)
	gofumpt -1 -w -s $(GOFILES)
	goimports -1 -w $(GOFILES)

lint:
	@echo "Running linter ..."
	golangci-lint run --timeout=10m -v ./...

test:
	@echo "Running tests ..."
	go test -v ./...

test-coverage:
	@echo "Running tests with coverage ..."
	go test -v -coverprofile=coverage.out ./...
	go tool cover -html=coverage.out -o coverage.html

generate-mocks:
	@echo "Generating mocks ..."
	@go install go.uber.org/mock/mockgen@latest
	@mockgen -source=internal/service/service.go -destination=internal/service/mocks/mocks.go -package=mocks

ci: deps fmt lint test build
```

## What the Author Is Saying

> "Благодаря WorkFlow мы можем тестировать и автоматизировать сборку проекта или заливать его, куда нужно."

GitHub Actions Workflows provide a complete CI/CD pipeline as code.

> "WorkFlow можно создавать на каждый репозиторий. Кроме того, может быть создано также несколько WorkFlow для одного проекта."

Workflows are repository-level configurations — multiple workflows per project are supported.

## Important Concepts

- **Deployment progression**: Single VM → Multi-VM with load balancer → Containers → Kubernetes orchestration → Serverless. Each step adds complexity but improves scalability.
- **nginx as proxy**: Simple `proxy_pass` directive forwards to Gateway service. Not production-ready without more setup.
- **GitHub Actions events**: `workflow_dispatch` (manual), `push` (on commit), `pull_request`, branch-specific triggers.
- **Checkout action**: `actions/checkout@v4.5.3` extracts source code from repository.
- **Makefile targets**:
  - `build`: Compile binary with version/time flags
  - `run`: Build + execute
  - `fmt`: Format code (gofmt, gofumpt, goimports)
  - `lint`: Run golangci-lint
  - `test`: Run all tests
  - `test-coverage`: Generate HTML coverage report
  - `generate-mocks`: Create unit test mocks from interfaces
  - `ci`: Full pipeline — deps → fmt → lint → test → build
- **Mock-based testing**: Uses `gomock` + `testify/assert` for unit tests with fake repository and Kafka publisher.

## Remember This

> Start with single-VM deployment for local dev, progress to containers → Kubernetes for production. GitHub Actions automates CI/CD — start simple, add complexity gradually.

> The `ci` Makefile target chains the full pipeline: `deps → fmt → lint → test → build`.

## Terms

- **Deployment strategies**: Single VM, multi-VM, containers, Kubernetes, serverless
- **nginx**: HTTP server/reverse proxy/load balancer
- **proxy_pass**: nginx directive to forward requests
- **Load balancer**: Distributes traffic across multiple instances
- **CI/CD**: Continuous Integration / Continuous Delivery
- **GitHub Actions**: GitHub's CI/CD platform using YAML workflows
- **Workflow**: YAML file defining CI/CD pipeline (.github/workflows/)
- **workflow_dispatch**: Manual workflow trigger
- **runs-on**: OS environment for workflow execution
- **Checkout action**: GitHub action to extract source code (actions/checkout@v4)
- **Steps**: Ordered commands within a job
- **uses**: References a pre-built action
- **Makefile**: Build automation tool
- **golangci-lint**: Go linter
- **gofumpt**: Opinionated Go formatter
- **goimports**: Go import sorter
- **gomock**: Go mock generation library
- **testify/assert**: Go testing assertions
- **Mock**: Test double simulating an interface
- **Unit test (*_test.go)**: File containing Go test cases
